# DEVPLAN-v0.23:让 youkai "会打会修" —— 每条发现给出利用方案 + PoC 文本 + 修复

> 交付对象:实现者(DeepSeek)。配 ADR-006(点头)、v0.14(探针)、v0.13(白盒)读。
> 背景:真实使用反馈 —— agent 找到了漏洞,但"只说存在,不说怎么打、怎么修",用起来不觉得强。
> 目标:每条**已验证或高可信候选**的发现,产出三样人话内容:**① 怎么利用(利用思路 + PoC 请求/载荷/脚本文本)② 影响评估 ③ 怎么修**。
> 这是档 2、**只产文本给人审阅、youkai 从不自动发 PoC/不自动打穿**(ADR-006 红线不动)。web + 二进制都做。

## 0. 现状缺口(已核实)

- 二进制侧有 `pwn_template`/`impact_proof`/`web_poc` 的**骨架文本**,但很浅(占位骨架,不针对具体发现)。
- **web 侧完全没有"怎么打"的产出** —— 只检测到"存在反射/越权/SSRF",不给利用思路和 PoC。
- **报告里没有"怎么修"(remediation)** —— 只有 counter(反证),没有修复建议。

所以 youkai 现在是"报告漏洞存在",不是"讲清这条怎么利用、怎么修"。补上这段,它才从扫描器变成会分析的 agent。

## 0.5 不可动摇(红线,一个不松)

- **只产文本,绝不自动发/自动打**:PoC 是给操作员审阅、由操作员在授权范围内**自己**运行的文本。youkai 不发 PoC 请求、不自动利用、不拿 flag。这是档 2 和 ADR-006 的核心,不动。
- **只给已验证/高可信候选配利用方案**:对 `verified` 或证据充分的 candidate 才产 PoC;纯假设(code-only)不产 PoC(避免为没证实的东西编利用)。
- PoC 文本里**不含真实凭据/会话/数据**;用占位符(`<YOUR-SESSION>`、`<TARGET>`)。利用思路基于已归一的证据,不塞目标响应正文。
- 档 3(自动打穿/自动发 PoC)仍不在本仓库、编译期墙外;本版只做"产出怎么打的文本"。

## 1. web 利用方案生成 `internal/web/exploit_plan.go`(P0,最缺)

**目标**:对每条 web 发现(越权/注入/SSRF/XSS/路径穿越/文件上传…),产一份结构化"利用方案"文本。

**能力**:`web_exploit_plan`(档 2,只产文本)—— 入参 finding id。按发现类型(kind)套对应模板,填入该发现的具体证据(端点、参数名、request_id),产出:
- **利用思路**:这条为什么能利用、攻击者能拿到什么(如"IDOR:换 id 即可读他人订单")。
- **PoC 文本**:具体请求/载荷骨架,带占位符(`curl -H "Cookie: <YOUR-SESSION>" https://<TARGET>/orders/<OTHER-ID>`),**标注"由你审阅后在授权范围内自行运行,youkai 不发送"**。
- **验证法**:怎么确认利用成功(看什么响应特征),仍是"你自己跑了看"。

**按 kind 的模板(至少覆盖现有检测类)**:sqli/ssti/ssrf/path/cmdi/xxe/upload/idor-bola/bfla/open-redirect/反射XSS/JWT弱配置/OAuth弱配置。每类给"思路+PoC骨架+验证法"。

**实现要点**:模板 + 发现证据填充,纯文本生成,不发请求;写进 artifact 目录 + 关联 finding;产出标 `tier2`、`generated-text`、`never-sent`。

**验收**:对一条 IDOR candidate 产出带占位符的 PoC(换 id 的请求)+ 修复建议;对 SSTI 产出 `{{7*7}}`→真实载荷思路(文本);PoC 里无真实 cookie/数据;youkai 不发任何 PoC 请求。

## 2. 修复建议 `internal/report`(P0,"怎么修")

**目标**:每条发现在报告里带 `remediation`(怎么修),和 counter 并列成为四样证据之外的标准字段。

**改法**:
- `FindingReport` 加 `Remediation` 字段;按 kind 给修复模板(sqli→参数化查询/预处理;idor→对象级授权校验;ssrf→出站白名单+禁用重定向;xss→上下文编码+CSP;jwt→校验 alg、设 exp;…)。
- 报告(MD/HTML)和披露包里显示"怎么修"。
- 修复建议是通用最佳实践(不含目标细节),安全、可直接给甲方。

**验收**:每条已知 kind 的发现报告里有具体可操作的修复建议;披露包含修复段;未知 kind 如实留空不编。

## 3. 接进对话与托管流 `web/chat.js` + 引擎(P1)

**目标**:托管只读侦察跑完、有了验证/高可信发现后,对话里 AI **主动给出**"我找到了 X,这条这么利用(PoC 见下)、这么修;要我把利用方案整理成文档吗?"——仍是产文本、点头才生成,不自动打。

**改法**:
- 托管 run 停在 idle 且有发现时,AI 小结里带"发现 + 怎么打的概要 + 怎么修",并给"生成完整利用方案文本"的按钮(调 `web_exploit_plan`,档 2,产文本)。
- 明确措辞:youkai 给的是**方案和 PoC 文本**,打这一步由操作员自己做(符合定位,也符合 CTF 场景——它把"怎么拿 flag"讲给你,flag 你自己去拿)。

**验收**:托管跑完,对话里能看到"发现→怎么打→怎么修"的小结 + 一键生成方案文本;生成的是文本不是攻击动作。

## 4. 二进制利用方案做深 `internal/binary/tier2.go`(P1)

**目标**:把现有 pwn/impact_proof 骨架从"通用占位"做成"针对该样本发现的具体方案":结合 binflow 假设(v0.18)+ checksec 结果,给出针对性的利用思路 + gdb/pwntools 脚本骨架 + 缓解措施。仍只产文本、不执行。

**验收**:对一个有 binflow 假设(如 argv→system)的样本,产出针对性的利用思路 + 脚本骨架 + 修复(编译加固/输入校验);不执行样本。

## 5. 收尾

- README 更新:youkai 现在"找到漏洞 + 说清怎么打(PoC 文本)+ 怎么修",利用由人审阅后自行执行。
- bench/靶场加一条"发现→方案"的验收样例。

## 落地顺序

1. 模块一(web 利用方案)+ 模块二(修复建议)—— 最缺、最直接提升"觉得强",先做。
2. 模块三(接对话托管流)。
3. 模块四(二进制做深)、模块五(文档)。

**每步验收锚点**:只产文本、绝不自动发 PoC/不自动打穿;只给 verified/高可信候选配方案、纯假设不配;PoC 无真实凭据/数据;
修复建议可操作;档 2 点头才生成;档 3 仍墙外;`go test ./...` 全绿;门禁仍过。

## 一句话

让 youkai 从"报告这里有个洞",升级成"这个洞这么利用(方案和 PoC 给你)、这么修" ——
会分析、会给方案,强在这;但扣扳机那一下永远是人,不是它。CTF 的 flag 它把路给你指明,flag 你自己去拿。
